# RFC-0007 · 本源北桥 v0.2（Northbridge Context Protocol）

**Spec ID:** `northbridge/0.2`
**Status:** Draft — 参考实现已通过验证（`node northbridge/verify-northbridge.mjs`，18/18，连跑两轮一致）
**取代:** 北桥 v0.1（`.claude/hooks/load-state.mjs` 里那个「一次性编译 bundle」）
**原则:** 相关性只能在**知道目标之后**判断。在没有目标的时刻做筛选，是猜，不是筛。

---

## 0. 这版改什么

修 RFC-0006 §0 诊断出的**根因三：北桥插错了插槽。**

北桥的职责是「CPU 此刻需要知道世界的哪一部分」。而它被装在 `SessionStart`——**那一刻还没有 goal**。

后果是可测的：

| 版本 | 实现 | 实测 |
|---|---|---|
| v0.1 | 抓 mtime 最新的一份学历 | 19 条已验证事实只进来 9 条，且无人知道 |
| v0.2 首版 | 全量 bundle + 字符预算 | 冲破预算 9400/9000，被静默砍掉，头部还写着「装载 46/51」 |
| v0.2 修补 | 预算核算 + 头部上界 + 轮转分配 | 装载率上去了，学历涨到 96 条时仍丢 28 条 |

三次都在同一个约束下打转：**在不知道要干什么的时刻，只能公平分配，不可能精准。** 轮转已经是那个位置上的天花板。

之前拒绝架构文档的 `context.request` 时给的理由是「只有一个消费者，它不需要跟自己发请求」。**那个理由是错的**——不是消费者少，是**消费者被放在了错误的时刻**。

## 1. 把北桥拆成两个时刻

```
SessionStart          UserPromptSubmit
（还没有 goal）        （goal 第一次出现）
     │                        │
   boot                    request
     │                        │
 开机自检                 相关性检索
```

### boot —— 不猜相关性

`SessionStart` 给的是**确定需要的东西**，不含任何猜测成分：

- 当前任务（mtime 最新那份）**全量**：目标 / 当前状态 / 全部已验证事实 / 近 4 条决策 / 下一步
- 其余学历**只列目录**：路径、标题、已验证事实条数、未完成项数
- 体检行（指纹、只读位、孤儿、不可复核 source）

判据 N1.5 锁住一条容易被忽略的性质：**boot 必须是确定性的**——同样的磁盘状态跑两次输出逐字节相同。一旦里面混进猜测，这条就红。

实测：8 份学历 96 条事实时，boot **3868/6000 字符**，无截断，8 份一份不漏。（v0.2 同样数据下是 8660/9000 且丢 28 条。）

### request —— 有 goal 那一刻才检索

`UserPromptSubmit` 是 goal 第一次出现的时刻。这一轮只调入：

- 与 goal 相关（相关度 ≥ 0.35）
- **且本会话尚未注入过**（按 `factId` 去重，账本 `.claude/nb-injected-<sid>.json`）
- **且不属于当前任务**（boot 已全量给过）

**没有相关的就一条都不注入。** 每轮硬塞是另一种浪费，而且会把真正的信号淹掉（判据 N2.2）。

相关度是字符 bigram + 词元的重合度，除以 `sqrt(|goal|)` 而不是 `|goal|`——否则长目标会被稀释成零分。**这是第一版，不上向量**：现有语料 96 条，上向量索引是过早工程，同 RFC-0005 §5 对 SQLite 的判断。

## 2. 真正的不变量

三个版本换了三种实现，但要锁的东西自始至终只有一条：

> **磁盘上的已验证事实，不会因为预算而永久不可见。**

判据 **N3.1** 直接验它：遍历磁盘上每一条已验证事实，要么出现在 boot 里，要么能用它自己的 claim 当 goal 检索到。二者皆无 → 红。

这条判据不关心实现是「抓最新一份」「全塞轮转」还是「boot + request」。**判据锁不变量，不锁当下的实现**——这是 RFC-0005 §7 那条教训（B5.2 因为锁了能力边界而过期）的直接应用。

于是「预算装不下」不再等于「这辈子看不到」：目录里列着，相关时会被调入。

---

## 3. hook 绝不能挡住用户说话

`UserPromptSubmit` 挡在用户每一句话前面，所以 `context-request.mjs` 的失败模式只有一个：**静默放行**。

- stdin 是垃圾 → exit 0，无输出（N4.1）
- 提示短于 4 字（「继续」「好的」）→ 不触发检索（N4.2）
- `import` 失败 / 编译异常 → exit 0，无输出

判据 N4.1–N4.4 把这条钉死。宁可不注入，也不能让北桥成为阻塞点。

## 4. 判据搬家（不许静默删）

北桥 v0.1/v0.2 的装载判据原本住在 `verify-benjing.mjs`（B1.1/B1.2/B1.3/B1.5/B1.6/B1.7/B1.8）——它们锁的是「开会时装载什么」，那是北桥的职责，不是本境的。这版整体搬到 `verify-northbridge.mjs` 的 N1/N2/N3。

搬走之后 `verify-benjing.mjs` 新增一条 **B1.0**：主动跑一遍北桥验证器并断言退出码 0。

> **搬家不能等于消失。** 判据从一个文件挪到另一个文件，中间必须留一条能被 grep 到的、且真的会跑的链子。

本境判据数 49 → 43（搬走 8 条 + 新增 B1.0，B1.4 重写为直接测 `findStates` 而不再绕 bundle 文本）。

## 5. 刻意没做的事

- **向量检索 / 嵌入**：96 条语料，bigram 重合度够用且可解释。等出现「明明相关却检索不到」的实测案例再谈。
- **多轮累积的 goal**：只用本轮 prompt，不拼接历史。会话越长目标漂移越大，拼历史会让相关性越来越糊。
- **把 request 结果写回学历**：调入是读路径，不产生新事实。写回是学堂的事。
- **跨项目检索**：只扫本仓库。

## 6. 未决问题

1. **`minScore = 0.35` 是拍的**，没有调参依据。目前实测行为合理（无关目标零注入、相关目标精准命中），但缺乏系统性评估。
2. **`UserPromptSubmit` 的实际触发尚未在真实会话中验收**——本 RFC 的判据是喂 stdin 跑 hook 脚本，属于契约层验证。真实注入效果要下一条用户消息才看得到。
3. **去重账本按 session 隔离且只增不删**：会话极长时账本会一直涨；且换会话后会重新注入同样的事实。
4. **boot 的「当前任务」仍按 mtime 判定**：多会话并发时，最后被碰的那份不一定是你要干的那份。
5. **相关性只看 `claim + source` 文本**，不看任务的 `goal` / `current_state`。整份学历级别的相关性尚未利用。
